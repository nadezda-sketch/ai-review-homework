## Пример 2. Java: риск NullPointerException и неявная логика ошибок

### Исходный код
```java
public class MailService {  
  private final UserRepository userRepository;  
  private final MailClient mailClient;  

  public MailService(UserRepository userRepository, MailClient mailClient) {    
    this.userRepository = userRepository;    
    this.mailClient = mailClient;  
  }  

  public void sendWelcomeEmail(Long userId) {    
    User user = userRepository.findById(userId);     
    mailClient.send(user.getEmail(), "Welcome!");  
  }
}
Мой промпт
Ты — опытный ревьюер Java-кода. Проведи код-ревью. Контекст: сервис отправляет приветственное письмо пользователю. Метод userRepository.findById(userId) может вернуть null. Критерии проверки: 1) Корректность (NPE, обработка отсутствия пользователя). 2) Обработка ошибок (исключения при отправке). 3) Читаемость. 4) Тестируемость. Ограничения: не предлагай крупный рефакторинг без причины; не выдумывай методы, которых нет в стандартном API. Формат ответа: для каждого замечания укажи приоритет (blocker/major/minor), что не так, риск, как исправить. Вот код: [код приложен]

Ответ ИИ (сокращенно)
1. Пропуск проверки на null (Blocker). userRepository.findById(userId) может вернуть null. Без проверки метод дальше передаёт user в mailClient.send(), где вызов user.getEmail() вызовет NullPointerException. Риск: крах метода в рантайме. Исправление: добавить явную проверку if (user == null) или использовать Objects.requireNonNull.

2. Отсутствие обработки ошибок при отправке (Major). Нет информации о том, как MailClient.send() обрабатывает ошибки. Риск: тихо пропущенное письмо пользователю, welcome-цепочка обрывается без видимых следов. Исправление: обернуть вызов в try/catch с логированием.

3. Читаемость / Отсутствие логирования (Minor). Метод не логирует ни входные параметры, ни факт успешной отправки. Риск: повышенное время отладки при инцидентах. Исправление: добавить log.info(...).

4. Тестируемость (Minor). Если MailClient.send() не бросает проверяемое исключение, unit-тест не сможет симулировать сценарий ошибки. Исправление: убедиться, что MailClient.send() бросает исключение при сбое.

## Пример 3. Go: SQL-инъекция через конкатенацию строки

### Исходный код
```go
package handlers

import (
    "database/sql"
    "fmt"
    "net/http"
)

func Orders(db *sql.DB, w http.ResponseWriter, r *http.Request) error {
    status := r.URL.Query().Get("status")
    query := fmt.Sprintf("SELECT id, total FROM orders WHERE status = '%s'", status)
    _, err := db.Query(query)
    return err
}
Мой промпт
Ты — опытный ревьюер Go-кода с фокусом на безопасность. Проведи код-ревью. Контекст: HTTP-обработчик Orders принимает параметр status из query string и выполняет SQL-запрос к таблице orders. Критерии проверки: 1) Безопасность (SQL-инъекции). 2) Корректность (обработка ошибок, управление ресурсами). 3) Читаемость. 4) Тестируемость. Ограничения: не предлагай крупный рефакторинг без причины; не придумывай новые библиотеки. Формат ответа: приоритет (blocker/major/minor), что не так, риск, как исправить. Вот код: [код приложен]

Ответ ИИ (сокращенно)

5. Читаемость (Minor). Отсутствие обработки rows маскирует намерение функции. Исправление: добавить комментарий или дописать логику чтения строк.
